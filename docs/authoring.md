# Skill 创作约定

## 1. 先定义契约

创建目录前，先回答以下问题：

1. 用户会用哪些自然语言触发它？哪些相似请求不应触发？
2. 完成一次工作流需要哪些输入？哪些输入可以自动发现？
3. 最终产物是什么？只生成草稿，还是会修改文件或提交到外部系统？
4. 哪些步骤具有外部副作用，需要确认、权限或凭据？
5. 哪些部分适合指令，哪些必须用脚本保证确定性？
6. 如何用代表性案例验证它确实有用？

## 2. 创建最小结构

```text
skills/<skill-name>/
└── SKILL.md
```

`SKILL.md` 的最小格式：

```markdown
---
name: skill-name
description: 清楚说明这个 skill 做什么，以及遇到哪些请求时应使用它。
---

# Skill title

用祈使句写出 Agent 应遵循的流程。
```

命名规则：

- 目录名与 `name` 完全一致。
- 使用 1–64 个小写英文字母、数字或连字符。
- 不以连字符开头或结尾，不使用连续连字符。
- 名称描述能力，不绑定某次任务、日期或具体项目。

## 3. 渐进式组织内容

只有确实需要时才添加这些目录：

- `references/`：规则、字段字典、系统说明、输出规范等按需读取的资料。
- `scripts/`：抓取、转换、校验、格式化等需要稳定复现的动作。
- `assets/`：周报模板、示例文件、图像或其他交付资源。
- `agents/`：如 `openai.yaml` 等客户端专属的展示、策略或依赖元数据。

保持 `SKILL.md` 易读且聚焦，建议不超过 500 行。文件引用使用相对于 skill 根目录的路径，避免多层引用链。

## 4. 处理个人工作流

- 把稳定的工作方法写入 skill，把会变化的账号、项目名、收件人、日期范围等留作运行时输入。
- 模板可以入库；真实周报、公司内部数据、访问令牌和私有链接不得入库。
- 对“生成”“预览”“提交”做清晰区分。默认先产生可检查的结果，不要把外部写操作藏在普通生成步骤中。
- 对缺失信息设置明确的降级策略：能安全推断的就推断，会改变结果或产生外部副作用的就询问。

## 5. 验证与维护

至少覆盖以下案例：

- 典型触发请求。
- 容易误触发的相邻请求。
- 缺少必要输入。
- 外部工具或数据源不可用。
- 重复运行是否安全。
- 输出是否满足格式和隐私要求。

把这些案例连同期望结果写进 `skills/<skill-name>/references/validation.md`，动 skill 之前先照着走一遍。

完成修改后：

```powershell
python scripts/validate_skills.py
```

随后更新 `skills/README.md` 中的目录说明，以及根 `README.md` 的 skill 列表。

## 6. 登记分类

在根目录 `catalog.json` 的 `skills` 对象中添加同名条目，并引用一个或多个已有分类：

```json
{
  "skills": {
    "skill-name": {
      "categories": ["work", "effective"]
    }
  }
}
```

这里只展示需要新增的片段，不要覆盖文件中的 `version` 和 `categories`。分类用于浏览、筛选和将来生成安装集合；skill 的真实目录仍必须位于 `skills/<skill-name>/`。
